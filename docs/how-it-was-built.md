# How this library was worked out

This is the record of how the formats and the dialog structure behind TeklaHelper.DrawingAttribute were found, in the
order it happened, and how each finding was checked. CLAUDE.md holds the rules that came out of it; this file explains
where they come from, so that they can be checked again, for example for another Tekla version.

## The problem

The Tekla Open API only sees the objects a drawing view shows: `view.GetAllObjects()` returns nothing for a part the
view hides, so a view must be created with the right object settings and filter from the start. Most of those settings
are not API properties. They live in **attribute files** that API objects load by name:

```csharp
new GADrawing("PLAN", "plan_100");            // plan_100.gd (+ .gd.more, .gd.filter, .gd.npfilter)
view.Attributes.LoadAttributes("detail_20");  // detail_20.vi (+ .vi.filter, .vi.npfilter)
```

The goal: build those files from C# objects that look like the Tekla dialogs, and write them so that Tekla reads them
exactly like the files its dialogs save.

## 1. The key-value format, from real files

**Sources.**
- About 2000 attribute files in 190 extensions under `D:\Tekla\Structures\2025.0\Environments`, including Japanese
  (code page 932) and Korean (949) environments.
- The model folders under `D:\Tekla\Models`.
- Files the maintainer saved from the Tekla 2025 dialogs: `TEST.*`, then `VIEW-TEST.vi`, `DRAWING-TEST.gd` and
  `test-ad.ad`, in `D:\Tekla\Models\New model\attributes`.

**Findings.**
- One `key value` per line, CRLF. The first line names the code page (`encoding 1252`), except in `.more` files.
- Strings are quoted, but quotes inside them are not escaped: the value runs from the first quote to the last. Line
  breaks inside a string are `\x01`.
- Doubles are written with six decimals (`20.000000`); check boxes are 0 / 1; `<key>_en` is the check box in front of a
  dialog control.
- Mark contents (`*.ContentString*`) are XML documents that declare UTF-8, and Tekla writes them as UTF-8 even inside a
  932 file. Some Japanese files mix both encodings inside one value, which no decoding can write back unchanged.
- Old files have no encoding line and prefix every key with the dialog name (`view_dial.`, `gdraw_dial.`, ...); old page
  files do the same (`vpm_dial.`).
- `.more` files prefix keys with an object type that differs between environments (`adraw_dial_attributes` or
  `assemblydrawing_attributes` for `.ad.more`, ...). Dates are Unix seconds, `-2147483648` meaning empty.

**Design that came out of it.** Every value keeps the bytes it was read from, so an unchanged value is written back byte
for byte whatever its encoding. Keys keep their order; a new key goes to the end.

**Check.** `SampleFileTests` reads every file under a folder, writes it back and compares the bytes
(`TEKLA_ATTRIBUTE_SAMPLES`). It runs on the environments and the model folders after every format change.

## 2. Filter files, checked against Tekla itself

Filter files (`.vi.filter`, `.gd.filter`, `.vf`, `.SObjGrp`, ...) are a block format: `TITLE_OBJECT_GROUP`, then one
`SECTION_OBJECT_GROUP` of ten tokens per row (parentheses, enabled, category, property, labels, condition, value,
parentheses, And/Or).

**Method.** A throw-away net48 console referenced Tekla 2025's `Tekla.Structures.dll` and called
`Tekla.Structures.Filtering.Filter.CreateFile` for every operator, value type and nesting shape, without Tekla running.
The library's output was compared with those files.

**Findings.**
- Token lines end with a space; spaces inside a token are `\x02`.
- Numbers are written `G15`, dates `MM/dd/yyyy`, booleans `True`/`False`, empty text `Empty`. The API formats numbers
  with the current culture (`2,5` on a Vietnamese Windows); the dialogs and this library use the invariant culture.
- A root group is wrapped in parentheses; the last row of a group takes the operator of the outermost item ending there.
- `Filter.CreateFile` writes the same bytes for every file type; only the extension differs.
- Tekla's reader cannot read `Custom*` (user-defined attribute) rows, not even its own.
- `Tekla.Structures.Filtering` needs `BinaryFormatter`, so it fails on .NET 8+.

**Decisions.**
- The library does not reference Tekla. Embedding the DLL with Costura was tried and dropped: it would ship five
  Trimble DLLs and load them side by side with another Tekla version.
- The filter property catalog (`FilterProperties.cs`) is generated by reflection from
  `Tekla.Structures.Filtering.Categories` (`tools/FilterCatalogGenerator`), so its categories and names are Tekla's.

**Checks.** `TeklaOracleTests` (net48, only where Tekla is installed) compare the catalog and every filter file the
library writes with `Tekla.Structures.Filtering`, byte for byte. 3378 shipped filter files round-trip, as rows and as
an expression tree.

**Limits found later.**
- A value holds at most 1023 bytes: the `Value` column of the filter dialog's table (`RuleTable` in
  `TeklaStructures.aid`) is `char LENGTH=1023`, a 1024-byte buffer.
- A filter holds at most 1000 rows, as the maintainer tested in Tekla.
- `Tekla.Structures.Filtering` writes and reads back longer values and more rows without error (tested with 5000
  characters and 1500 rows), so these limits belong to Tekla itself.

## 3. Which files the Open API reads

The maintainer confirmed:
- For a view the API reads only `name.vi` + `.vi.filter` + `.vi.npfilter`.
- For a GA drawing it reads only `name.gd` + `.gd.more` + `.gd.filter` + `.gd.npfilter`.

That is exactly what the Save button of the properties dialog writes. The files of single pages (`.vg`, `.vpm`, `.vf`,
`.gdgr`, ...) are only for the Save / Load buttons of each page in the dialogs. The view dialog writes no `.vi.more`.

A page file holds exactly the keys of one section of the `.vi` without the prefix. This was checked value by value
between `TEST.vi` and `TEST.vg`, `TEST.vpm`, ... (test `SubDialogFiles_MatchTheTreeOfALoadedView`), which mapped every
page file extension to its prefix. Drawing page extensions (`.gdgr`, `.gpm`, `.adgr`, ...) were matched by key set.

## 4. Probing a running Tekla

**Method.** To learn what each key does, `tools/TeklaProbe` was run against the maintainer's open drawing:
1. Insert a temporary view with the coordinate system of an existing one.
2. Load copies of `TEST.vi` with one key changed at a time (`view.Attributes.LoadAttributes` + `Modify`).
3. Read the drawing objects back (`Part.Attributes`, ...) and compare.
4. Delete the view and the probe files.

**Findings.**
- **Tekla keeps an attribute file by name for the whole session.** A file written again under a name it already loaded
  is not read again, so every load needs a new name.
- **An empty filter file (`Count= 0`) makes the view show no objects at all.** The library therefore writes no filter
  file when a filter has no rows, and deletes an old one of that name. The dialogs write "no filter" as one row
  `co_part proNAME == Empty`.
- The `_en` check boxes do not gate `LoadAttributes`; they only matter to the dialog's Modify button.
- Colour numbers pass through unchanged; small numbers (1–7) found in dialog files are valid colours. Line types are
  0–7; 8 and above make Tekla drop the whole file.
- Part `draw_as` is `Part.Representation` (flags 1 Outline, 2 Symbol, 4 WorkshopForm, 8 Exact, 16 BoundingBox,
  32 BaseBox, 64 SolidWithPartialProfile).
- Each part key maps to an API property (`draw_hidden` → `DrawHiddenLines`, `PartHatch.*` → `FaceHatch`, ...); some keys
  have no API property at all (`inner_contours`, `FilletEdges`, ...).

## 5. View and drawing share their pages

**From the files.** The key sets of `VIEW-TEST.vi` and `DRAWING-TEST.gd` were compared section by section: 24 sections
are identical apart from the prefix (`vp.` ↔ `dp.`, `vpm.` ↔ `dpm.`, `vg.` ↔ `dgrid.`, `vfilter.` ↔ `dfilter.`, ...).
`test-ad.ad` showed the same for the assembly family under its own prefixes (`dv.`, `grid.`, `dnp.`, `drmark.`,
`dsurfmark.`). It also showed that assembly drawings have no reference object page (`drefobj.`) and have an assembly
dimensioning section `dcd.` of their own.

**From the dialog definition.**
- The GA drawing properties dialog (`gr_gdraw_attrib`) opens the same sub-dialogs as views: its "Part mark..." button
  opens `gr_vpm_attrib`, "Part..." opens `gr_vp_attrib`.
- `gr_vp_attrib` and `gr_dp_attrib` declare the same data structure (`gr_dp_at_t` plus the hatch structures).
- The 2025 View properties dialog lays the same structures out as panels.

**Design that came out of it.** One class per page, used by every host with that host's prefix (`PageHost`,
`PartMark.PrefixFor(host)`).

## 6. Decoding the dialogs into classes

To give every control of the View properties dialog a typed property, the dialog definition itself was decoded instead
of being typed in by hand.

**Source.** `D:\Tekla\Structures\2025.0\bin\TeklaStructures.aid` holds every Tekla dialog in a compiled resource format
("RES 1.1"): a pool of strings and a token stream of objects (dialogs, panels, tabs, group boxes, controls) and their
attributes. In a control:
- `MEMBER` is the key in the attribute file;
- `VALUEINT` is the value an option stores;
- `CALLBACKPARAMETER` names the check box in front of it.

English labels come from the `string_utf8` objects.

**Pipeline.**
1. `tools/DialogDecoder/extract.py` reads the dialog `gratViewAttributes`: the tree on the left and one panel per page
   (`PanelPart`, `PanelPartMark`, ...), with tabs, group boxes, controls, options and the sub-dialogs their buttons open.
   It also takes keys from the older dialogs with the same structure, for keys the 2025 panels no longer show. It writes
   one JSON file per page into `tools/DialogClassGenerator/Dialogs`, and marks what is decoded and what is inferred
   (which text label belongs to which control).
2. `annotate.py` adds the Open API enum of each option list and the value statistics of real `.vi` files: which values
   files hold, inside and outside the dialog's menu.
3. `tools/DialogClassGenerator` turns the JSON into `src/TeklaHelper.DrawingAttribute/Pages/Generated/*.g.cs` (the drawing
   object files and their pages into `DrawingObjects/Generated`):
   - tabs, group boxes and sub-dialogs become nested classes;
   - toggles become `bool` with the dialog's on/off values, option lists become enums, colours `DrawingColor`, line
     types `DrawingLineType`;
   - keys the dialog does not show go to an `Advanced` group, so that every key of the dialog files has a property.

**Corrections driven by the files.** The decoded dialog was checked against what Tekla actually writes:
- A control copied from another page can store "on" differently there. `for_main` is 2 in the bolt mark menu but 1 in
  260 part mark files, so the files decide.
- A missing key reads as the dialog's default, or else the value most files hold. This keeps a missing hatch background
  from reading as black.
- Values that files hold but the menu does not offer get an enum member (`vg.GridObjectGridOn 0`, `DrawingWeld.DrawAs 0`).
- One check box in the `.aid` names its member without the struct of its control; the files tell the right key.

Corrections go into the decoder, never into the JSON by hand, so that decoding again keeps them.
`tools/DialogDecoder/README.md` describes how to decode another Tekla version and compare the result.

### Other Tekla versions

The View properties dialog of Tekla 2020 and 2026 (`TeklaStructures.aid` of each, decoded with the 2025 sample files, so
only what the dialogs declare is compared) has the same 25 pages as 2025. Differences in the keys:

| Version | Compared with 2025 |
| --- | --- |
| 2026 | Adds `BarAttr.fill_color` and `MeshAttr.fill_color` (Reinforcement and Neighbor reinforcement, "Fill color" in the Visible lines group of the bar and mesh appearance tabs). Nothing removed. |
| 2020 | No section lines, own hidden lines or center line settings for parts, neighbor parts and pour objects (`section_*`, `own_hidden_*`, `center_*`); no Rebar assembly tab (`AssAttr.*`); no "IFC property export" check box on the filter page (dialog only, no key). Colour controls declare dialog defaults that 2025 no longer declares. |

Decision: the page classes follow the newest dialog, so the JSON files are now decoded from Tekla 2026. That added
`FillColor` to the bar and mesh appearance tabs (its XML comment says it is new in 2026) and moved the section and own
hidden lines of pour objects from `Advanced` to their Appearance groups. Controls of the `Advanced` group with a generic
label ("Color", "Type") are now named after their key (`ReferenceColour`, `BoltColour`), so that a property name does
not change meaning when a new dialog moves controls around.

The 2020 result matches the shipped environment files: most of them were saved by older versions and lack the
`section_*` / `center_*` keys. Not checked yet: what Tekla 2020 does with keys it does not know, and files saved from
the 2020 and 2026 dialogs.

### The pages of the drawing properties

The drawing files hold about 1000 keys more than the pages shared with the view: the view page of the drawing, section
views, detail views, dimensions and automatic dimensioning. A report from another project (every key of a Tekla 2020
`.gd` and `.vi` without a typed property) led to decoding them too.

**Finding the dialogs.** For each key prefix, the members of every dialog of the 2026 `.aid` were matched with the keys
of `DRAWING-TEST.gd` and `test-ad.ad`:

| Keys | Newest dialog that shows them | Other dialogs with the same keys |
| --- | --- | --- |
| `dview.` / `dv.` | `gr_ga_view_attrib` ("View..." of the GA drawing properties) | `gr_dv_attrib`, the assembly panel `PanelContentViewCreation` |
| `dc.` | the "Section view" panel of the assembly drawing properties (the GA dialog only shows the start number) | `gr_dc_attrib`, `gr_csym_attrib` (section mark, keys under `SectionMark.`), `gr_section_label_attrib` |
| `DetailLabel.` | `gr_detail_symbol_attrib` | `gr_detail_label_attrib` |
| `dd.` | `gr_dd_attrib` ("Dimension...") with the sub-dialog "Place..." (`dimpl.`) | — |
| `Dimensioning.` (GA only) | `gr_gdcd_attrib` ("Dimensioning...") | — |
| `dcd.` (assembly family only) | `gr_adcd_attrib` | `gr_wdcd_attrib`, `gr_cudcd_attrib` |

The rows of label texts of the view, section and detail pages (`ViewLabelMarkA1` ... `A5`, `SectionMark.SectionMarkA1`,
`SectionMark.ViewLabelMarkA1`, `DetailMarkA1`, ...) have exactly the 26 keys of the view's `ViewLabelMarkA1.`: they reuse
the class `ViewLabelMark` instead of 650 more generated properties.

**Decoding.** `extract.py` decodes each page from its newest dialog or panel and fills the keys it does not show from the
other dialogs; those controls keep the tab and group of their own dialog (`dialogPath`), so that `aLabelFrontView`
becomes `Views.Label.ViewName.FrontView` rather than an unexplained `FrontView` in `Advanced`. A radio button without a
label takes the text label after it ("Fit by parts", "Section depth"), only on these pages, so that the released view
pages keep their names. `annotate.py` reads the drawing files for the value statistics and maps the dimension menus to
the Open API enums (`DimensionSetBaseAttributes.DimensionTypes`, `DimensionValuePrecisions`, `DimensionValueFormats`,
`CombineFormats`, ...), which name the enum members (`DimensionType.Absolute`, `DimensionPrecision.OnePerEight`).

**Generating.** The view page of the drawing extends the class `DrawingViewCreationSection` released in 1.0.0: the
generated part skips the keys and member names of the hand-written part (view creation, scale, shortening switch, label
colour, height and position), and its `SetDefaults()` assigns those properties too, except the View creation table and
the 3D view file, whose shipped values name files of an environment. The other pages are new classes. The released
enums only gained members; of the existing generated pages only the XML comment of `PartMark.Advanced.Create` changed.

**Defaults.** `SetDefaults()` of a page cannot tell a GA from an assembly drawing, and their shipped files disagree on
dimensions and views. `CreateDefault()` therefore keeps, for these pages, the value most files of the same drawing type
hold, as before: its output did not change.

**Checked in Tekla.** An assembly drawing created from a `CreateDefault()` .ad with changed values (view extension for
neighbor parts, openings symbol, datum level, skew part shortening; dimension type, colour and text height; cutting
line colour, section mark symbol colour and arrow length; fewer automatic dimensions) showed every one of them through
the Drawing API (`View.Attributes`, `StraightDimensionSet.Attributes`, `SectionMarkBase.Attributes`, the number of
dimension sets).

**What stays untyped.** A test (`EveryKeyOfAFileSavedFromTekla_IsTyped`) checks every key of the files saved from the
dialogs. The exceptions: check boxes (`SetAllEnabled`), page file names, `dl.placing_direction` (no dialog of 2020, 2025
or 2026 shows it) and the fixed fields of the filter pages (`vfilter.partname_enable`, ...: no dialog shows them since
the filter rows moved to the `.vi.filter` file, and a probe view showed that Tekla 2025 ignores them: `vfilter.partname
"BEAM"` with any `filtering_type` kept all 85 parts, a filter row kept 9).

### Drawing object files: dimension properties

The drawing editor saves the properties of its objects in files of their own: `.dim` for dimensions, `.drtxt` for
texts, `.lev` for level marks, ... The dialog-name table of `TeklaStructures_application.dll` lists them (`dim_dial`
`.dim`, `.drtxt`, `.note`, `.sbl`, `.lev`, `.gln`, ..., `dim_prefix_mark_dial` `.dimension_mark`). The first one typed
is `.dim`:

- The dialog `gr_dim_attrib` writes 100 of the 109 top-level keys of `common/system/standard.dim`; the rebar dimension
  dialog `gr_rebar_dim_attrib` shares the structure and gives six more keys that the .dim files Tekla 2025 writes hold
  (`RebarSubgrouping`, `TaperedSkewedReinforcementGroup`, ...). `--file-folders` lets the decoder see the keys of every
  .dim file of the environments and models, not only of the sample.
- Each of the nine marks (prefix, postfix, tags A to G) holds the 116 keys of every mark plus four rebar dimension mark
  keys. Its dialog `gr_dim_mark_attrib` names its members without their struct (`height`, `frame_type`); it declares the
  structs `gr_mark_unit_at_t`, `gr_mark_frame_at_t`, `gr_mark_font_at_t` before `gr_mark_at_t`, so `height` is
  `FontAttr.height` although a top-level `height` exists too. The decoder resolves the struct from the file keys.
- Menus whose items are constant names (`DIM_REINFORCEMENT_STRAIGHT`) get readable members (`Straight`); the dimension
  menus take the names of the Open API enums.

Checked in Tekla 2025: `new StraightDimensionSetAttributes("name")` read a library-written file with the changed type,
precision, format, short dimension placing, text height, frame, colour and exaggeration, and a dimension created with
those attributes in a probe drawing kept them.

### The other drawing object files

**Which files.** The attribute classes of Tekla.Structures.Drawing that take a file name (`Text.TextAttributes(name)`,
`Part.PartAttributes(name)`, ...) list the objects the Open API loads settings for; the dialog table of
`TeklaStructures_application.dll` and the `.aid` give the dialog of each (`text_dial` → `gr_text_attrib`, ...). Few of
these types have a modern sample among the shipped files (none for `.sbl`, `.rev`, `.fdg`, `.dcha`, `.sc`, `.drmsh`,
`.drmp`), so each dialog was saved from Tekla 2025 itself: a drawing macro, run with `Operation.RunMacro` while a drawing
was open, displayed each dialog (`akit.Callback("acmd_display_attr_dialog", "<dial>", "main_frame")`) and pressed its
Save as with the name `OBJECT-TEST` (widget names from the `.aid`). The 41 files hold every key of every modern shipped
file of their type, except four rebar dimension mark keys that older versions wrote; 40 are kept next to the other
dialog files (the `.dim` one would change the sample counts of the released dimension pages).

**Which extension each class reads.** A probe copied every `OBJECT-TEST.<ext>` under a name of its own with every double
set to 7.77 and every colour to 163, constructed every attribute class from every name and searched the result for the
markers. The map is in CLAUDE.md; the surprises: `CloudAttributes` reads the polygon file `.gpg`,
`ReinforcementMeshAttributes` reads `.drbr` (not `.drmsh`), `EmbeddedObjectAttributes` reads `.fdg` for images too, and
`Mark.MarkAttributes(drawingObject, name)` reads the associative note file `.note`, not `.pm`. The section mark file is
`.cs`, the extension of C# macros as well: the statistics and the tests take only `.cs` files that start with an encoding
line (or the legacy prefix `csym_dial.`).

**Reusing the view pages.** Thirteen dialogs write exactly the key set of a page of the View properties (the part mark
dialog the keys of `vpm.`, the grid and grid line dialogs those of `vg.`, ...), so their files use the released page
classes. The others got pages of their own, decoded from their dialog. Dialogs of one structure (text, symbol, level mark
and revision mark share `gr_text_at_t`; part, surface treatment and pour `gr_part_at_t`; the six graphic objects; the
five link objects) are each other's other sources, so a key one dialog does not show is typed where another shows it.
Two decoder additions were needed: the part dialog names the members of two structures with the same members
(`STRUCT=gr_part_hatch_at_t` and `gr_section_hatch_at_t`, member `hatch_name`), which the prefix shared by the file keys
cannot tell apart, but the structure's name can (`PartHatch.`); and the associative note takes the keys its dialog does
not show from the mark panels of the View properties, whose members carry the page prefix (`vpm.`), stripped. The JSON
files of the existing pages stayed byte for byte the same.

**Names.** Menus that show only pictures keep `ValueN` members, as before, except where the meaning is known: the weld
symbols of the drawing weld mark store the values of `Tekla.Structures.Model.BaseWeld.WeldTypeEnum`,
`WeldContourEnum` and `WeldFinishEnum` (picture `w_type_10` stores 10, the API's fillet weld), and take those names.
The "Edge/Around" and "Workshop/Site" menus are named in the order of their label, which their XML comments say is not
checked. The part and pour object dialogs order the Representation menu differently from the view's part page; they
use the released `Representation` enum all the same (`EnumReuse`).

**Defaults.** A file that uses the page of another file type (a `.pm` file the view's part mark page, a `.rdim` file
the dimension pages) does not take that page's `SetDefaults()`, whose values come from the `.vi` (or `.dim`) files: its
table holds the values most of its own shipped files hold (`text_colour` 155 in `.pm` files, 161 in the views' `vpm.`),
else those of the dialog file.

**Checked in Tekla 2025.** A file of each type written by `CreateDefault()` with one value changed was loaded with its
attribute class, and the class showed the value: 36 checks, among them `arrow` 1/2/3 = `Arrowhead.ArrowPosition`
Start/End/Both, `scaling_type` 3 and 8 = `ScaleXY` and `ScaleBestFit`, the hatch colours under `PartHatch.` and
`SectionHatch.`, and the frame colour of a mark (the top-level `line_colour`).

### Mark and label content

The marks and the label rows store what they show as XML in the `ContentString` keys: 17 143 values in 1 289 files,
with `<Element subType="23">` for a property, `<UserText>`, `<LineFeed/>`, `<Symbol>`, `<Frame>` with mark content
inside, `<Template>` and a `<Format>` per element. The number is what counts, and it is not the Open API's: the API's
`PropertyTypes` equal the file numbers for 1 to 53 and 57 to 70 only (the merged mark settings 54–56 are in another order,
the mesh size is 71 in files and 73 in the API, the scale 79 and 80).

**The numbers.** The Open API served as the translator: a file holding only `<Element subType="N">` was loaded with
`Mark.MarkAttributes` (from a `.note` file), `View.ViewAttributes`, `SectionMarkAttributes` and `DetailMarkAttributes`
for every N from 1 to 110, and the element the API returned was noted. All four agreed for every N, so the numbers are
one table for every kind of mark; the lists of the API's `*PropertyElementTypes` say which elements each kind offers.
Further probes showed that `name` and `value` are ignored (an element named `PART_POS` with number 82 is the view
name), that `override` and `hidden` change nothing the API reads, and that a frame with `frame_id` 0 (as the library
first wrote) loses its elements: they read as following the frame. These probes loaded a `.note` file (associative
note), whose tables are by kind of object: a part read `ContentString1`, a reinforcement group `ContentString4`.

**The content tables.** The mark pages have a table per kind of part, bolt or bar instead ("Mark content of" in the
dialog). The maintainer noticed the four tables of the reinforcement mark; in the shipped files the first holds the
elements of single bars, the second spacing and number, the third only merged mark settings, the fourth the mesh size.
A probe wrote a `.vi` whose every content key held its own name, inserted a view of a probe GA drawing with it and read
every mark: main parts showed table 1, secondary parts 2, reinforcement groups 2, site bolts 1. For the rest the model
was changed for the run and put back: a single bar and a mesh added to a slab (tables 1 and 4), one bolt made a
workshop bolt (2), one assembly added to another as a sub-assembly (its main part 3, its secondary part 4). The dialog's
menu values (Single 0, Group 1, Mesh 2) are not the table numbers. Marks merged with `MergeMarks` still showed table 2;
table 3 is the merged mark set, which the Open API cannot read. The same probe on a `.note` gave every part table 1,
every bolt 2, every reinforcement 4 and a reference model `ReferenceObjectContentString`.

**The mark dialogs of the drawing editor.** The maintainer asked whether the Part mark properties dialog of the drawing
editor uses the four tables the same way. It does not: loaded with a `.pm` whose tables named themselves and applied
with Modify to every part mark of a probe view, it gave main, secondary and sub-assembly parts all table 1, whatever the
file's `CurrentContentTableNumber`. The decoded dialog (`gr_pmark_attrib`, 2025 and 2026) has a single content table and
no "Mark content of" menu. Saving such files again from each mark dialog showed what each one reads and writes: the part
and bolt mark dialogs read `ContentString1` and write it into all four keys, the connection, reinforcement and surface
treatment mark dialogs into 1, 2 and 4 (3 kept), the pour mark dialog reads `PourContentString` and writes it there and
into `ContentString1`. The library gives each of these files an `Elements` that does the same. Loading such a file into the
existing view `C BOT` of a FOOTING drawing (`LoadAttributes` + `Modify`) left the content of its reinforcement group
marks as it was. A review of the sample application then showed that this is not the rule: in a view just inserted with
the environment's `standard.vi`, the part marks took the new content when the file was loaded the same way. What keeps
the marks of `C BOT` (placed or edited in the drawing, or being reinforcement marks) was not looked at.

**Round trip.** Content Tekla wrote must be written back as it was. The reader keeps the attributes of each element in
their order, the layout (a line per tag, or one line), the line break (two line feeds in some older files), whether a
text sits on lines of its own, and whether `>` is written `&gt;` (Tekla did both). Every content of the environments and
models is written back the same, except 25 values that mix UTF-8 with the code page. Two kinds of damage Tekla's own
files hold are read: an attribute without value (`value= subType`, 390 values, repaired) and a raw `<` in a text
(`<< Mark >>`, 18 values, kept raw). A review pass found the last one, and that the library numbered frames by changing
the content it wrote; frames are now numbered per writing. A second review (1.3.1) found that content with an element
outside any `<MarkPart>` could not be compared, that the comparison ignored the grouping into MarkParts, that new text in
content read with a raw `<` could become a tag (now only a `<` no name can follow stays raw), and that one-line content
whose text held a line feed was taken for the line layout (the layout is now told by the line break after the XML
declaration alone).

**Picture-only menus.** The leader line menus of the text, symbol, level mark, revision mark and note dialogs show only
pictures, the pictures are compiled into Tekla, and the Open API does not read the value. A macro opened each dialog
and selected each value (`akit.ValueChange` takes the value, not the index; `akit.TabChange` brings the tab), and
`PrintWindow` captured the dialog window without bringing Tekla to the front; the enlarged pictures named the values
(no leader line, leader line, base line, base line with an arrow left or right; the level mark's leader line with or
without the level symbol).

**The object files in their dialogs.** A macro loaded every `CreateDefault()` object file of the library, one value
changed, into its dialog (Load) and saved it again (Save as): all 41 dialogs took the files, kept the value and every
key, apart from what they normalise or compute.

**Checked in Tekla 2025.** Content built with `MarkContent` — view name in Tahoma green 5.158, a red text, scale, line
feed, symbol, a frame with a part position, a user-defined attribute in millimetres with two decimals, a template — was
written to a view label, a part mark, a section mark and a detail mark, in both layouts, and the Open API read every
element with its format.

## 7. Default settings

**Probe.** A view with red, dashed, hidden-line parts was loaded with a file holding only `view_scale`: the parts lost
the red, the dashes and the hidden lines and got colour 6, solid, no hidden lines — the values of the Korea
`standard.vi`, the environment of the model (colour 6 is no dialog default and appears in 4 shipped files only). A new
view from that file did the same. So **a key a file lacks takes the value of the environment's standard file**, and an
incomplete file draws differently from one environment to the next.

**Design.** `CreateDefault()` writes every key a file saved from the dialog has, plus the keys of the newer dialog:
- page keys: `SetDefaults()` of each page, one property assignment per control. The value is the one most shipped
  files hold (ASCII only, so every code page can store it, only when at least three files have the key, never an empty
  font or a zero text height or colour), else the dialog's own default, else the value of the dialog file; the page's
  check boxes are ticked. Shipped files come first because the dialog's declared defaults are sometimes just the first
  menu item (Solid for every line type, where no shipped file holds Solid for center, own hidden or reference lines);
- other keys (layout, view creation, dimensioning, section and detail views, the old filter dialog, ...): the most common
  shipped value, else the value of the dialog file. Keys that name a layout or an attribute file use names every
  environment has (`ga`, `multi`, `assembly`, `single`, `cu`, `standard`), titles and descriptions are empty;
- single-part and cast unit drawings use the keys of the assembly drawing file: their newer shipped files have the same
  `dcd.` keys, the older ones hold keys of earlier versions;
- on top, `Pages/DefaultSetup`, the library's own choices for views that show their objects to the API: parts exact with
  hidden lines and the center line of main beams; part, bolt and grid lines black; bolts, welds, surface treatments,
  the grid and connected neighbor parts (outline) shown; part marks with the assembly position, no bolt marks, no filter;
  view labels black; views 1:20, fitted to the parts, not shortened;
- drawings also get the empty user-defined attribute fields of a dialog `.more` file.

A review of the first version found what the rules must avoid: the old filter dialog's switches turned on, values taken
from one odd shipped file (`inf`), layouts that exist only in the Default environment, surface treatments hidden by the
dialog default. A second, adversarial pass found the line types and the mark texts above.

**Check in Tekla** (model "New model", several rounds, every drawing and file removed afterwards):
- A temporary view loaded from a `CreateDefault()` file showed exact parts with black solid lines, black dashed hidden
  lines, dash-dot center lines, slashed reference lines, at 1:20, with marks: the file's values, not the Korea
  standard's colour 6.
- A GA, an assembly, a single-part and a cast unit drawing were inserted from `CreateDefault()` files. In every view Tekla
  created, the main parts were exact, black, with hidden lines (and the center line of the main beam); neighbor parts
  were outlines in their default red. The results were the same on every run.
- The views of assembly, single-part and cast unit drawings take their settings from the view properties file named in
  the View creation table (`dv.aDrawingViews`: view type, Off 0 / Auto 1 / On 2, label, .vi name, decoded from
  TeklaStructures.aid). With the names empty they use the object and mark settings of the drawing file; with a
  `CreateDefault()` view file named there (`Views.SetViewAttributeFile`), they took its scale (1:20) and part settings.
  The same Off / Auto / On values are those of `cre_front_view` and the other view switches, and the 3D view switch
  stores On as 2. Tekla follows the table, not the switches: a default file whose shipped-majority switches said the
  bottom view was off still got a bottom view, because its table said Auto. The library therefore reads and writes the
  switches through the table (`CreateTopView = ViewCreation.On` changes the table row and `cre_top_view`), and
  `CreateDefault()` writes the switches from the table. With the top view On and the bottom view Off, Tekla created the
  front and top views and no bottom view.
- The 3D view behaves differently: with an empty file name in the table, a cast unit drawing's 3D view used the
  environment's `standard.vi` (Korea: 1:75, outline, colour 6), while the other views used the drawing file's settings.
  `CreateDefault()` still clears the names, because the shipped defaults name files that exist only in some
  environments (`new_standard_5`, `cu_3D_view`, `single_3D_view`); naming a `CreateDefault()` view file with
  `SetViewAttributeFile` made every view, the 3D view included, exact, black and 1:20.
- The online examples created a GA drawing whose plan views, loaded from `CreateDefault()` files, showed 85 parts and,
  filtered on `Name = COLUMN`, exactly the 10 columns; loading a profile filter into the views of the open drawing left
  exactly the 13 parts with an I profile in both views.

## 8. How the work was checked

**Tests.** xUnit on net48 and net10.0:
- unit tests for every format rule;
- the generated pages walked by reflection on every host: every property writes its own key under its page prefix and
  reads back what it wrote;
- assigning a property its own value changes no byte;
- the README examples.

**Real data checks.**

| Check | Run with |
| --- | --- |
| Round trip of every attribute and filter file | `TEKLA_ATTRIBUTE_SAMPLES` = the environments and the models |
| Page files match their page; every key of the dialog files has a property | `TEKLA_VIEW_DIALOG_SAMPLES` = the folder of dialog files |
| Filter files equal Tekla's | `TeklaOracleTests`, automatic where Tekla 2025 is installed |

**Reviews.** Separate review and attack passes found real bugs that were fixed, each with a test:
- `for_main` read the wrong "on" value, so assigning a property its own value rewrote it in 2828 places;
- old page files with the `vpm_dial.` prefix did not import;
- hexadecimal values (`label_colour 0xFFFFFFFF` in a dialog file) read as the default;
- saving could leave a half-written set when a companion file could not be encoded;
- exported page files carried the wrong file name keys (Tekla writes `out_file ""`, and `aInFile` / `InFile` in two pages).

**In Tekla.** The sample application's online examples were run on the maintainer's model. A GA drawing with two plan
views loaded from generated `.vi` files: the API found 85 parts in the unfiltered view and exactly the 10 columns in the
view filtered on `Name = COLUMN`.

## 9. What the library is now

- **Format layer.** `AttributeValue`, `AttributeCollection`, `AttributeFileFormat`, `TextEncodings`: byte-preserving
  reading and writing.
- **Files.** `AttributeFile` and its companions (`.more`, filters): loading parses every file before applying any;
  saving encodes every file before writing any.
- **Dialog pages.**
  - Generated classes for every page of the View properties dialog and of the drawing properties.
  - `MarkPages` and `ObjectPages` group the mark and object pages.
  - `ViewProperties` (`.vi`) and the drawing files (`.gd`, `.md`, `.ad`, `.wd`, `.cud`) expose them, with the prefixes of
    each host.
  - The files of the property dialogs of the drawing editor (`DrawingObjects`): 41 types, from `.dim` and `.drtxt` to
    the marks, links, graphic objects and reinforcement.
- **Filters.** `FilterFile` (rows, byte-preserving), an expression tree, and the generated `FilterProperties` catalog.
- **Samples.** `samples/`: twenty offline examples and six that run against Tekla.

## 10. Not settled

- What `override="1"` in the format of a mark element does: the Open API reads the element's font with or without it,
  and no dialog control writes it; whether the drawing draws the element's own font without it was not looked at.
- Why the reinforcement group marks of an existing view kept their content when other view properties were loaded,
  while the part marks of a new view took it.
- Table 3 of the reinforcement mark (merged mark settings) was not seen read, and `ContentString3` / `ContentString4` of
  the bolt mark, `ContentString3` of the associative note (surface treatment by the files) and the tables of the
  neighbour part and neighbour reinforcement marks were not probed.
- The weld menus Edge / Around and Workshop / Site are named from the order of their pictures, not from a capture
  (`KeyNotes` says so in the XML comment).
- The legacy key prefixes (`<dialog>.`) of 14 object file types are taken from the dialog names; no shipped legacy file
  of those types exists to prove them.
- `.vpro` and `.cpbr` have no sample file and no class.
- `for_main` of bolt marks: the menu stores 2, many files hold 1; both read as visible, but Tekla's behaviour for each
  was not probed.
- Some enum values in shipped files have no known meaning (named `ValueN`), among them the released `LeaderLineType`
  of the mark pages, whose menu is pictures only; the leader line menus of the object files were named from captures.
- The marks of drawing objects are files of the dialogs only: no attribute class of the Open API reads `.pm`, `.sm`,
  `.jm`, `.rm`, `.surfm` or `.pom` by name.
- The dialog's column limits other than the value (127 bytes for category and property, 19 for condition and And/Or,
  0–3 parentheses per row) are documented but not enforced.
- `dl.placing_direction` has no control in any dialog; its meaning is not known.
- What Tekla 2020 does with the keys it does not know (the 70 keys newer dialogs added to `.gd` files).
